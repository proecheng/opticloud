## Outcome

Epic 9 established a repeatable static-governance pattern:

- Canonical JSON contract under `tools/<topic>/`.
- Manifest schema and static example that cannot fake real-world completion.
- Stdlib validator under `scripts/`.
- Focused pytest coverage under `tests/`.
- Operator runbook under `docs/runbooks/`.
- Dedicated `.github/workflows/ci.yml` path filter and hard-gate job.
- Optional real evidence mode under `reports/<topic>/<run_id>/...`.

The pattern now covers accessibility, observability, cost redlines, security P0 drills, WCAG 2.2 upgrade readiness, error i18n audit, unified governance dashboard handoff, and MLPS Level 2 evidence aggregation.

## What Worked

The strongest process improvement was the three-round adversarial review before implementation. It repeatedly caught boundary and closure gaps before code was written, especially fake-completion language, external-integration overreach, evidence path ambiguity, and status-sync ordering.

The post-implementation review also paid off. Repeated findings were fixed before merge, including status enum gaps, CI filter drift, upstream dependency drift, no-leak coverage gaps, real-evidence release-gate bypasses, and stale observed-state validation.

The strict GitHub ordering prevented status drift. Story files and sprint status were marked `done` only after PR CI passed, the PR merged, the remote branch was deleted, and local `main` was synced.

## Issues Found

Planning drift existed: `_bmad-output/planning/epics.md` labels Epic 9 as a 7-story epic, while sprint status and implementation closed eight stories after Story 9.8 was added from TT7 / E8 compliance evidence requirements. The implementation state is coherent, but planning documentation now undercounts Epic 9.

The sprint status statistics block is stale. It still reports early-project totals and percentages that no longer match the actual number of completed stories. This is a status-document maintenance issue, not an Epic 9 delivery blocker.

Several stories initially risked claiming real-world outcomes that are not present in the repo: real Grafana publication, real Prometheus/Grafana review, real DingTalk or Linear delivery, real P0 drills, full WCAG 2.2 AA conformance, real MLPS certification, real TSA issuance, real blockchain preservation, and real legal signoff. Those were narrowed into offline/static governance contracts with optional real-evidence modes.

## Repeated Review Themes

- Boundary issues: static governance assets must not imply external delivery, legal approval, certification, production release approval, or real operator execution.
- Drift issues: validators must compare committed observed state, upstream contract metadata, CI path-filter blocks, and source files instead of trusting static lists.
- Data consistency: real evidence needs exact enums, full required-domain coverage, one-to-one artifact/hash parity, ticket-backed findings, and release blocking for unresolved P0/P1/P2 items.
- Dependency consistency: the Epic 9 pattern should remain stdlib-first and avoid `jsonschema`, SaaS SDKs, Prometheus/Grafana clients, browser audit tooling, ticket SDKs, TSA clients, or blockchain clients unless a later implementation story explicitly owns that integration.
- Closure: every story must keep the separate post-merge status-sync commit.

These are now represented as explicit evidence lanes, findings, or future operator processes rather than hidden assumptions.
